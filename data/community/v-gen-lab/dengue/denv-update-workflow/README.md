# DENV 2026 lineage-definition workflow

This workflow builds and publishes updated DENV Nextclade datasets from a
package of representative sequences and lineage labels. In addition to the
review artefacts, it assembles each final dataset under `results/` for manual
publication.

The representative-tree NEXUS files supplied in the input package are the
topology source of truth. The workflow converts each one to clean Newick,
checks that its tip IDs exactly match the representative FASTA, and passes it
to `augur refine`. It does not infer a replacement topology with `augur tree`.

## Inputs

The update-specific input bundle is kept in `input/package/`, so a future
update can replace or edit it in one place. It contains:

* `DENV{1,2,3,4}_representatives.fasta`
* `sequence_lineages.csv`
* `test_set.csv` and `DENV{1,2,3,4}_test_set.fasta`

All files that are not generated by this workflow are recovered from the
newest timestamped release for that serotype under the configured
`dataset_history_root` (normally
`nextclade_data/data_output/community/v-gen-lab/dengue/denv*/`). This includes
the reference, source README, pathogen JSON and genome annotation. The test FASTA is
copied as `sequences.fasta`, and the annotated `results/denv*/tree.json` is
copied as `tree.json`.

During assembly, the source README receives the data-use notice selected by
`data_use_notices` in `config/config.yaml`. The notice text lives under
`config/data-use/`; edit these inputs rather than generated READMEs. A delimited
block is replaced on subsequent releases so the notice is not duplicated.
Both the notice file and assembly script are tracked as assembly-rule inputs.
Assembly also updates the inherited scope sentence to describe the current
`unassigned` result for sequences from other serotypes.

The pending CHANGELOG entry lists new terminal lineages by comparing the
current inherited definitions with the frozen baseline selected by
`baseline_version`. Rows with `gene=clade` express inherited markers and are
excluded from the lineage list. The baseline and current definitions are
explicit inputs to assembly, so a change to either refreshes the generated
CHANGELOG.

The initial mapping records the accepted README portion of F1 in the
[PR #478 review](https://github.com/nextstrain/nextclade_data/pull/478), dated
2026-09-24: DENV-1/2 receive the Restricted-Use notice; DENV-3/4 receive a general
Pathoplexus notice. This uses the review's findings, not an independent recount.
The README notice mapping is curated and must be reassessed when inputs or
their terms change. Assembly does not
query current terms or automatically infer that a restriction has expired.
The accepted provenance portion of F1 is recorded in
`config/auspice_config_d{1,2,3,4}.json`: Pathoplexus and GenBank, with their URLs,
are exported automatically to `meta.data_provenance` by `augur export`.
The accepted per-sequence metadata portion of F1 uses the local snapshot
selected by the metadata run manifest. It preserves `dataUseTerms`,
`dataUseTermsRestrictedUntil`, and `dataUseTermsUrl` from Pathoplexus, together
with the accession and sequence URL in the snapshot and `data-use.tsv`.
Following [the recommendation in PR #478](https://github.com/nextstrain/nextclade_data/pull/478#issuecomment-5832432377)
and [Nextstrain's guide](https://docs.nextstrain.org/en/latest/guides/pathoplexus.html),
tree tips use `PPX_accession`, `INSDC_accession`, `dataUseTerms`, and
`restrictedUntil`. The associated `*__url` columns produce clickable accession
and terms links in tooltips. `dataUseTerms` is also a coloring option in all
four Auspice configs. **Augur >=31.4.0 is required** for native link export.
The INSDC cross-reference for Pathoplexus records comes from `insdcAccessionFull`.
The same snapshot supplies `geoLocCountry` for the `country` tip attribute,
including directly queried NCBI accessions.
Augur exports `country` as a coloring and geographic resolution when the
location has known coordinates; tips with no country metadata remain blank.
The raw `geoLocCountry` is retained in `data-use.tsv`. A small alias table in
`scripts/data_use.py` maps spelling variants to Augur's country names; values
without a known coordinate remain visible in the country coloring but may not
appear on the map.
Assembly also creates `data-use.tsv`, covering both representatives and examples;
keep this table with the dataset when distributing its sequences. Entries from
other sources have blank Pathoplexus fields, not inferred OPEN status.

The snapshot contains its retrieval time, API data version and source URL, and
SHA-256 hashes of the eight input FASTAs. Missing accessions, conflicting terms,
unknown terms, and missing restriction dates cause an error. Expired restrictions
are not silently relabelled: the recorded API values are preserved.
Start each new dataset update with the metadata-aware entry point:

```bash
python scripts/update_dataset.py --cores 16
```

Before starting Snakemake, this command fetches current Pathoplexus and NCBI metadata,
checks coverage and validity, and freezes a new copy under `input/metadata-runs/`.
Each run contains `snapshot.json`, a field-by-field `changes.json` (including
country and data-use changes, plus added/removed accessions), and `run.json`
recording the snapshot checksum and workflow configuration. Comparison uses the
last validated refresh in this directory, initially the `data_use_snapshot`
configured in `config/config.yaml`. `--previous-snapshot PATH` selects another
comparison baseline. Existing snapshots are never overwritten.

If the request fails, a required accession is absent, metadata is invalid, or
the input FASTAs change during collection, the command stops before starting
Snakemake. There is no automatic fallback to stale metadata. The same immutable
snapshot is used throughout the run. These checks cover Pathoplexus and recognized
NCBI nucleotide accessions. NCBI EFetch is queried in batches for the exact version
present in the input (for example, `.1` is never silently replaced by `.2`).
NCBI location, collection date, record update date, resolved accession, retrieval
time and source URLs are saved under `ncbi` in the snapshot; only country and
accession links are added to the displayed metadata. Changes are included in the
same audit report. NCBI records are not assigned Pathoplexus OPEN/RESTRICTED terms.
GISAID identifiers and local names such as `EHIE21409Y22` are ignored by collection
and keep blank source-specific fields. Input sequences and example sets are unchanged.

To inspect only the metadata update, use `--metadata-only`. To prepare metadata
and preview the workflow, use `--dry-run`; this still performs a fresh query.
To explicitly reuse recorded metadata without a network query:

```bash
python scripts/update_dataset.py --cores 16 \
  --snapshot input/metadata-runs/RUN_ID/snapshot.json
```

Replay checks the snapshot against the eight input FASTA hashes and records a
new replay manifest. Older snapshots remain readable, but cannot provide NCBI
metadata or INSDC cross-references that were not collected at the time. Use a
fresh run to populate these fields. This reproduces the metadata selection; reproducing the
entire dataset also requires the same workflow, configuration, dependencies and
other input files. The README notice mapping remains a reviewed configuration;
reassess it if the change report shows a change in restriction status.

Direct Snakemake calls require an explicit `--config metadata_run_manifest=PATH`
from a prepared run. This prevents an ordinary update from silently using the
old configured baseline. The lower-level `scripts/snapshot_data_use.py` remains
available for standalone collection. The initial 2026-09-24 snapshot confirms
1,488 OPEN and 36 RESTRICTED accessions; replacing examples remains a separate
review decision.

The generated CHANGELOG begins with `## Unreleased` and the notes configured
in `release_notes`; it then preserves the changelog from that latest release.
The workflow replaces any pre-existing leading `## Unreleased` section, so
rebuilding a dataset does not duplicate the pending notes.

The supplied 2026-09-15 package has already been copied into `input/package/`.

## Run

```bash
conda env create -f environment.yaml
conda activate dengue-nextclade-2026
python scripts/update_dataset.py --cores 16
```

The main review artefacts are:

* `results/denv*/marker_report.tsv`: candidate marker panels, support and
  conflicts. Candidates are mutations on the branch entering the labelled
  class's MRCA, not mutations accumulated along the entire ancestral path.
  The configured 2–3-marker panels are evaluated jointly, and `Unassigned`
  representatives are retained in the outgroup when measuring specificity.
* `results/denv*/clades.proposed.tsv`: complete, machine-generated marker
  proposal for every labelled lineage in the current input package.
* `results/denv*/clades.inherited.tsv`: final definitions, including marker
  requirements inherited from named parent clades.
* `results/denv*/tree.json`: final Nextclade tree built from those inherited
  definitions, representative metadata, lineage colors, and nucleotide and
  amino-acid mutations. Amino-acid mutations are generated by `augur translate`
  from the ancestral reconstruction and the dataset GFF3 annotation. Nextclade
  placement masks are derived per serotype from the first and last coding
  coordinates in that GFF3 and the reference FASTA length, using 0-based,
  end-exclusive ranges.
* The metadata generated from the current `sequence_lineages.csv`
  representatives is temporary: it is used by `augur export` and then removed.
* `results/denv*/color_ordering.tsv` and `colors.tsv`: lineage ordering and
  colors generated with `scripts/assign-colors.py` for `clade_membership`.
* `results/denv*/validation.tsv`: validation of the final inherited dataset
  against held-out sequences and their expected lineage.
* `results/denv*/clades.diff.tsv`: row-level comparison with the versioned
  baseline. Rows are labelled `maintained`, `added`, or `removed`.
* `results/denv*/clades.version.json`: baseline/proposal SHA-256 hashes and
  comparison counts.
* `results/datasets/denv*/`: complete, reviewable assembled dataset. Publish
  this directory manually to `nextclade_data/data/community/v-gen-lab/dengue/`
  after review.

Do not promote `clades.proposed.tsv` to the final dataset without reviewing
lineages marked `needs_review` in the report and incompatibilities reported
against the baseline.

## Inherited markers in the final definitions

For each proposed clade, the workflow builds `clades.inherited.tsv`.
It adds an Augur `gene=clade` row when the NEXUS annotations identify a named
parent clade that also has a direct definition. This makes the child require
its own marker panel plus the complete marker set inherited from its parent.
This is the only dataset exported and validated by the workflow; there is no
parallel direct-marker-only release.

For manual curation, copy the inherited TSV to a separate reviewed definition
directory and edit that copy, never the generated result. Add a basal parent
definition before adding `child\tclade\tparent` rows: inheritance can only
refer to a parent clade that itself has at least one direct marker row.

## Definition versioning

`definitions/2025/denv*/clades.tsv` is a frozen copy of the previous release.
`baseline_version` in `config/config.yaml` selects the version used by the
comparison rule. This step reads the baseline and proposal without modifying
either. The comparison is by TSV row values: quotes, blank separator rows and
row order do not create differences. Duplicate rows are counted.

To review just the comparisons after marker proposals exist:

```bash
snakemake --cores 4 results/denv1/clades.diff.tsv results/denv2/clades.diff.tsv \
  results/denv3/clades.diff.tsv results/denv4/clades.diff.tsv \
  --config metadata_run_manifest=input/metadata-runs/RUN_ID/run.json
```

Copy the four complete proposal files to a separate review directory, correct
any incompatibilities manually, and keep a short review note describing those
changes. The reviewed directory must contain `denv1/clades.tsv` through
`denv4/clades.tsv`. Publish it under a new, never-reused version, declaring
the original proposals and review note as provenance inputs:

```bash
python scripts/publish_definitions.py --approved-root /path/to/reviewed \
  --parent-version 2025 --version 2026-01 \
  --input-file results/denv1/clades.proposed.tsv \
  --input-file /path/to/reviewed/review-notes.md
```

The publication command verifies TSV structure, stores the publication date,
declared input-file hashes, approved hashes and parent hashes in
`definitions/2026-01/manifest.json`, and refuses to overwrite an existing
version. It does not approve proposals automatically. Once the new version has
been reviewed, change `baseline_version` to `2026-01` for the next comparison
cycle. Keep `definitions/` and its manifest files together when moving the
workflow to another machine.
